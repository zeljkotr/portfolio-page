DevOps · Production Deployment · Zero-Trust Access

Bailiff Sentinel — Financial Anomaly Detection

Role Sole engineer — design, build, deploy, operate Stack Python, Flask, Gunicorn, SQLite, systemd, Tailscale, GitHub Actions Repository github.com/zeljkotr/bailiff-sentinel

A web application that analyzes Serbian bank statement exports (XML, inconsistent schema and encoding across branches) to detect a specific anomaly: a payment sent to one account, then quietly returned by the bank days later — usually a sign of a misdirected transfer. Because the tool handles real account data, it was built and operated with the same discipline as a small production service, not a personal script.

Design and operational decisions

  • Schema-agnostic parsing — automatically detects and flattens nested XML structures rather than hardcoding field names, and self-corrects encoding (UTF-8, UTF-16, CP1250) since exports vary by branch and settings.
  • Separate development and production environments — changes are validated on a test instance before reaching the server handling real financial data.
  • Managed as a systemd service — runs continuously, restarts automatically on failure, and survives server reboots without manual intervention.
  • No public network exposure — the production host has no open inbound ports; access is entirely through a Tailscale (WireGuard) mesh network.
  • Gated deployment pipeline — every push is tested and deployed automatically to a staging environment, but production sits behind a GitHub Environment approval gate, so a push alone never goes live.
  • Automatic, idempotent schema migrations — the database adds any missing columns on startup, so upgrades apply safely with no manual migration step or downtime.
  • Structured error handling — every error path returns a clean response rather than a stack trace, with debug mode explicitly disabled.
  • Redesigned anomaly detection — after finding a correctness bug in the original approach, which compared columns within a single row, refund detection was rebuilt to pair debit and credit rows by amount, direction and date proximity.
  • Deployment hardening — handled Python's externally-managed-environment restriction (PEP 668) by installing into a virtual environment, fixed SSH key authentication by tightening authorized_keys permissions, and scoped passwordless sudo to the single service-restart command the CI pipeline needs.
  • Concurrency tuning — SQLite runs in WAL mode with a busy timeout so concurrent requests do not hit database locks.

Deployment pipeline

  1. Change is pushed to the main branch; GitHub Actions runs the checks, then deploys automatically to staging and verifies it with a health check.
  2. Production deployment waits for explicit reviewer approval before it starts.
  3. The pipeline authenticates to the private network using short-lived, tag-scoped OAuth credentials — no standing VPN keys or open ports.
  4. It connects over SSH via the private network, pulls the latest code, installs dependencies, and restarts the service.
  5. Temporary credentials are discarded immediately after the run.

Key decisions

  • systemd over a manually run processEnsures the service recovers from crashes and survives reboots without anyone needing to remember to restart it.
  • Tailscale over a traditional VPN or open portReachable from every authorized device, including CI, without a static IP or any port exposed to the public internet.
  • Manual deployment gateProduction holds real financial data — a code push should never be equivalent to "go live."

The application itself runs five configurable checks (full and partial refund matching, duplicate transaction IDs, duplicate payments, statistical outlier detection), keeps a persistent history of uploads, supports manual false-positive marking, and exports findings to CSV and PDF.

Observability · Infrastructure as Code · Scalability

Observability, IaC and Scale-Out Lab for Bailiff Sentinel

Role Sole engineer Environment Self-built lab (VMware VM + AWS Free Tier), mirroring the production app Stack Prometheus, Grafana, Loki, Alertmanager, Terraform, Ansible, Nginx, Redis, PostgreSQL

A hands-on lab built around the real Bailiff Sentinel application to practice the production-grade tooling around it: monitoring, log aggregation, alerting, infrastructure as code, load balancing, and moving the data layer from SQLite to PostgreSQL.

What was built

  • Metrics and dashboards — Prometheus, node_exporter and Grafana in Docker Compose, plus custom application metrics exposed from Flask (parsed-file counters by status, anomaly counters by type, processing-time histograms) feeding a dashboard for parsing success, CPU, disk and anomalies.
  • Centralized logs — Loki and Promtail with automatic Docker container discovery, queried from the same Grafana instance.
  • Alerting — Prometheus alert rules (service down, high XML parsing failure rate, disk almost full) routed through Alertmanager to Telegram.
  • Terraform — provisioned an AWS EC2 instance, security group and generated SSH key pair within Free Tier limits, with terraform destroy after every session for cost control.
  • Ansible — idempotent playbooks (verified with clean no-change re-runs) that install Docker, deploy the app and manage the Redis, monitoring and database containers, with secrets kept in Ansible Vault. The full chain GitHub → Terraform → EC2 → Ansible → Docker → app was verified end to end over the internet.
  • Load balancing and sessions — Nginx with least-connections balancing across three app instances, health-based failover, and Redis-backed server-side sessions so users are not tied to one instance.
  • Gunicorn — moved the app from the Flask development server to Gunicorn with multiple workers, rolled out through the staging-to-production pipeline.

Key decisions

  • PostgreSQL instead of per-container SQLiteLoad balancing exposed that each instance held its own SQLite file. Migrated to a shared PostgreSQL database with a migration script run first in dry-run mode, preserving record IDs (4 batches, 1,552 transactions).
  • Compose and Ansible with clear ownershipEach container is managed by exactly one tool, which removed a conflict where Ansible and Compose both tried to own the same service.
  • Databases not exposed to the networkPostgreSQL and Redis are reachable only from the internal container network or loopback, never through a published port.

Virtualization · Migration · Storage

Physical-to-Virtual Migration of a Production Windows 10 Host to KVM on TrueNAS SCALE

Role Sole engineer — design and implementation Target KVM virtual machine, UEFI, 2 vCPU, 16 GiB RAM Stack Disk2vhd, QEMU, ZFS, dd, VirtIO

Designed and implemented a full P2V migration pipeline that moved a production Windows 10 environment from physical hardware into a KVM-based virtualization stack on TrueNAS SCALE, keeping the original system, its services and its network configuration intact.

Migration pipeline

  1. Imaged the live physical disk with Disk2vhd using VSS, so the image is consistent without taking the system offline.
  2. Converted the disk format from VHDX to RAW with QEMU.
  3. Provisioned a ZFS ZVOL on TrueNAS, sized for the image and tuned for performance.
  4. Imported the large disk image into the ZVOL with low-level dd operations.
  5. Created the KVM virtual machine, booted it and fixed the boot and driver issues below.
  6. Verified full functionality, including networking and services.

Problems solved

  • Boot failure — diagnosed a UEFI/BIOS mismatch and a missing bootloader that stopped the migrated system from starting.
  • Driver incompatibilities — deployed VirtIO drivers for disk and network so Windows ran with proper performance on KVM.
  • Large image handling — managed storage sizing and import of a large disk image on ZFS without disturbing other workloads.

Result

A fully functional virtual machine with improved portability, scalability and backup capability, replacing a single physical machine with a system that can be snapshotted, restored and moved.

Industrial Systems · Virtualization · Legacy Modernization

Legacy SCADA System Virtualization (Windows XP → VMware)

Role Sole engineer — conversion, configuration, validation Source Obsolete physical PC, Windows XP, Presezzi SCADA Stack VMware vCenter Converter, VMware Workstation

Migrated a legacy industrial SCADA system (Presezzi) from an obsolete physical computer running Windows XP into a virtual environment using VMware vCenter Converter and VMware Workstation. The machine controls live production equipment, so the goal was a faithful copy: the same operating system, the same software and the same communication with existing industrial equipment and PLCs.

What was done

  • P2V conversion — converted the production Windows XP machine into a virtual machine without changing its software environment.
  • Virtual hardware and deployment — configured the virtual machine so the legacy system sees hardware it is compatible with.
  • Network and IP migration — carried the network configuration over so existing equipment keeps reaching the system at the same addresses.
  • Serial and USB passthrough — configured device passthrough for the communication interfaces used to talk to industrial equipment.
  • Testing and validation — verified the SCADA software and its PLC communication in the virtual environment.
  • Backup and snapshot strategy — introduced snapshots and backups, which the original physical machine never had.

Result

The SCADA system is fully operational inside a virtual machine and can run on any available PC with no dependency on the original hardware. This removed the single point of failure of an aging machine, simplified backup and disaster recovery, and extended the lifecycle of the system without modifying the original software environment.
