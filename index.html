DevOps · Production Deployment · Zero-Trust Access Bailiff Sentinel — Financial Anomaly Detection Role Sole engineer — design, build, deploy, operate Stack Python, Flask, Gunicorn, SQLite, systemd, Tailscale, GitHub Actions Repository github.com/zeljkotr/bailiff-sentinel A web application that analyzes Serbian bank statement exports (XML, inconsistent schema and encoding across branches) to detect a specific anomaly: a payment sent to one account, then quietly returned by the bank days later — usually a sign of a misdirected transfer. Because the tool handles real account data, it was built and operated with the same discipline as a small production service, not a personal script. Design and operational decisions Schema-agnostic parsing — automatically detects and flattens nested XML structures rather than hardcoding field names, and self-corrects encoding (UTF-8, UTF-16, CP1250) since exports vary by branch and settings. Separate development and production environments — changes are validated on a test instance before reaching the server handling real financial data. Managed as a systemd service — runs continuously, restarts automatically on failure, and survives server reboots without manual intervention. No public network exposure — the production host has no open inbound ports; access is entirely through a Tailscale (WireGuard) mesh network. Gated deployment pipeline — every push is tested and deployed automatically to a staging environment, but production sits behind a GitHub Environment approval gate, so a push alone never goes live. Automatic, idempotent schema migrations — the database adds any missing columns on startup, so upgrades apply safely with no manual migration step or downtime. Structured error handling — every error path returns a clean response rather than a stack trace, with debug mode explicitly disabled. Redesigned anomaly detection — after finding a correctness bug in the original approach, which compared columns within a single row, refund detection was rebuilt to pair debit and credit rows by amount, direction and date proximity. Deployment hardening — handled Python's externally-managed-environment restriction (PEP 668) by installing into a virtual environment, fixed SSH key authentication by tightening authorized_keys permissions, and scoped passwordless sudo to the single service-restart command the CI pipeline needs. Concurrency tuning — SQLite runs in WAL mode with a busy timeout so concurrent requests do not hit database locks. Deployment pipeline Change is pushed to the main branch; GitHub Actions runs the checks, then deploys automatically to staging and verifies it with a health check. Production deployment waits for explicit reviewer approval before it starts. The pipeline authenticates to the private network using short-lived, tag-scoped OAuth credentials — no standing VPN keys or open ports. It connects over SSH via the private network, pulls the latest code, installs dependencies, and restarts the service. Temporary credentials are discarded immediately after the run. Key decisions systemd over a manually run process Ensures the service recovers from crashes and survives reboots without anyone needing to remember to restart it. Tailscale over a traditional VPN or open port Reachable from every authorized device, including CI, without a static IP or any port exposed to the public internet. Manual deployment gate Production holds real financial data — a code push should never be equivalent to "go live." The application itself runs five configurable checks (full and partial refund matching, duplicate transaction IDs, duplicate payments, statistical outlier detection), keeps a persistent history of uploads, supports manual false-positive marking, and exports findings to CSV and PDF. Migration pipeline Imaged the live physical disk with Disk2vhd using VSS, so the image is consistent without taking the system offline. Converted the disk format from VHDX to RAW with QEMU. Provisioned a ZFS ZVOL on TrueNAS, sized for the image and tuned for performance. Imported the large disk image into the ZVOL with low-level dd operations. Created the KVM virtual machine, booted it and fixed the boot and driver issues below. Verified full functionality, including networking and services. Problems solved Boot failure — diagnosed a UEFI/BIOS mismatch and a missing bootloader that stopped the migrated system from starting. Driver incompatibilities — deployed VirtIO drivers for disk and network so Windows ran with proper performance on KVM. Large image handling — managed storage sizing and import of a large disk image on ZFS without disturbing other workloads. Result A fully functional virtual machine with improved portability, scalability and backup capability, replacing a single physical machine with a system that can be snapshotted, restored and moved.
